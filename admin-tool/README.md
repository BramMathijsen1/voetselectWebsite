# Zorgverzekeringen updater

A small desktop tool for keeping `verzekeraars-data.js` (the data behind the "Check
uw vergoeding" modal on the website) up to date.

**Flow:** click the button → the app downloads the current `verzekeraars-data.js`
from the website server via FTP → if the "Gebruik Claude" checkbox is ticked,
Claude searches the web for each insurer's current podotherapie reimbursement
plans, using that download as its baseline (if unticked, you go straight to
reviewing/editing the downloaded data by hand, no research step) → you review and
edit the proposed changes in a window → on submit, the updated
`verzekeraars-data.js` is uploaded back to the website server via FTP, replacing
the old file.

There is no local copy of the data kept between runs — the live file on the server
is always the source of truth for "old" data (except in test mode, see below).
Claude only ever supplies *values*; the actual JavaScript is generated by
`data_model.generate_js()`, so a malformed model response can never produce broken
JavaScript on the live site. The reverse direction (`data_model.parse_js()`) reads
the downloaded file back into that same data shape — it understands only the
small, fixed subset of JS `generate_js()` itself produces, and never uses
`eval()`/`exec()` on downloaded content.

## Setup

1. Install Python 3.11+.
2. `pip install -r requirements.txt`
3. Copy `config.example.json` to `config.json` in this same folder and fill in:
   - `anthropic_api_key` — your Anthropic API key ([console.anthropic.com](https://console.anthropic.com)). You can also leave this as-is and set the `ANTHROPIC_API_KEY` environment variable instead — the app falls back to that.
   - `ftp_host`, `ftp_port`, `ftp_username`, `ftp_password` — your website's FTP credentials. These are used both to download the current file (as Claude's research baseline) and to upload the result.
   - `ftp_remote_path` — the absolute path to `verzekeraars-data.js` on the server.
   - `ftp_use_tls` — leave `true` unless your host doesn't support FTPS.

   **`config.json` contains secrets — it's already excluded via `.gitignore`. Never commit it.**

4. Run it:

   ```
   python app.py
   ```

### Testing locally — no FTP credentials needed

Set `"test_mode": true` in `config.json`. In this mode, the app never touches FTP —
it reads from and writes back to the local `verzekeraars-data-test.json` (path
configurable via `test_data_path`) instead, which plays the role "the website"
plays in the normal flow. Submitting in test mode saves your edits straight back
into that same file and **never uploads anything**.

Combine this with the "Gebruik Claude" checkbox on the main screen for two
different local test flows:

- **Checked:** Claude does real research (needs a valid `anthropic_api_key`),
  using `verzekeraars-data-test.json` as its baseline — good for testing the
  research + review flow without needing FTP access.
- **Unchecked:** no API key needed either — you go straight to the review window
  pre-filled with `verzekeraars-data-test.json`'s current contents, which you can
  edit and save. Good for testing the review UI itself (adding/removing
  verzekeraars, pakketten, links) in complete isolation.

The same "Gebruik Claude" checkbox also works outside test mode: unticked, the app
downloads the real site's current data via FTP and lets you hand-edit it directly
(no research call), then uploads your edits back via FTP on submit — a quick manual
edit path for small corrections that don't need a full Claude research pass.

Because Claude only runs for real (never stubbed), there's no simple deterministic
way to trigger the content-validation warning (see Security below) through the UI
alone. To exercise that warning dialog specifically, add a throwaway unit test that
calls `data_model.validate_response()` directly with deliberately bad content.

## Packaging as a standalone executable

Once it works via `python app.py`, package it with [PyInstaller](https://pyinstaller.org/):

```
pip install pyinstaller
pyinstaller --onefile --noconsole --name "ZorgverzekeringenUpdater" app.py
```

The executable is written to `dist/ZorgverzekeringenUpdater.exe`. Copy `config.json`
(filled in) into the same folder as the `.exe` — the app looks for it next to itself,
not bundled inside the executable, so you can update credentials without rebuilding.

## Notes

- The tool never overwrites the live file until you press **"Opslaan & uploaden naar
  server"** in the review window — closing that window with "Annuleren" discards the
  proposal.
- If the FTP upload fails, the tool tells you and nothing on the server has changed —
  fix the FTP settings and click the main button again (this re-downloads the current
  file and re-runs the research, since nothing was persisted locally).
- Research typically takes a couple of minutes since Claude runs multiple web
  searches per insurer.

## Security

Claude's response is grounded in live web search results — i.e. untrusted internet
content — so it's treated that way at every step, not just schema-validated and
trusted:

- **Claude never writes JavaScript.** Structured outputs constrains it to a fixed
  JSON shape; `data_model.generate_js()` is a deterministic Python template that
  renders the *values* into escaped JS string literals. Claude cannot supply
  executable code, only text that ends up inside `'...'`.
- **The downloaded file is never executed either.** `data_model.parse_js()` reads
  the FTP-downloaded `verzekeraars-data.js` back into data using a small hand-rolled
  tokenizer/parser — it never calls `eval()`, `exec()`, or a JS engine on that
  content. If the file doesn't match the shape `generate_js()` itself produces, it
  raises a clear error instead of silently executing or misinterpreting it.
- **Content, not just shape, is checked.** A JSON schema guarantees a field is a
  *string*, not that the string is safe to render — `data_model.validate_response()`
  flags any plan/link text containing `<`/`>` or a link that isn't a plain
  `http`/`https` URL, and the app blocks with an explicit warning (listing exactly
  what was flagged) before you ever see the review window.
- **The page itself doesn't trust the data either.** `script.js` builds the
  vergoeding modal's dropdown and insurer links with `textContent`/DOM properties,
  never `innerHTML` built from this data — so even content that somehow passed the
  checks above still can't execute as HTML/JS in the browser. This was fixed
  alongside the admin tool, since the tool is what started feeding this data
  from an LLM's web research instead of a human typing it by hand.
